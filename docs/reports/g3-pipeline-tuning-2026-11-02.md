# G3 流水线方案演进与取舍（2026-11-01 15:00 — 2026-11-02 02:30）

本文件记录全量池目标生成这条流水线在实施过程中**每一次方案变化**：改了什么、为什么改、优点、缺点、实测数字、最后怎么定的。所有数字都来自本机实测（`tc-hk-h20-02-ide`，AMD EPYC 9K84，128 逻辑线程 / 64 物理核，8×H20-3e 143 GB），不是外推。

## 0. 最终选择（当前冻结配置）

| 项目 | 取值 |
|---|---|
| 组大小 | 400 件 |
| A1/A2 并发 | **22 个进程**（单组生产） |
| A1/A2 缓冲区 | `--prefetch-groups 4`，常驻补货线程每 10 s 检查 |
| A4 分片 | **10 个**（8 卡，前两张卡各 2 片） |
| 磁盘闸门 | `--min-free-gb 60` |
| 压缩守护 | `compact_g3_targets.py` watch 模式，120 s 一轮 |
| 监控 | 本地 8771，含 15 分钟窗口的实时速率与 ETA |
| 实测 | A1/A2 ≈0.15 件/秒、A4 ≈0.12–0.15 件/秒、负载约 140 |

**选它的理由**：A1/A2 与 A4 抢同一批 CPU，此消彼长；6 分片时 A1/A2 最快（0.187）但 A4 只有 0.067（积压会撑爆磁盘），12 分片时反过来（A1/A2 0.107 / A4 0.180）。10 分片是两者的折中，两侧速率接近，积压稳定。

## 1. 清单构建：线程池 → 进程池

| | 方案 A（原） | 方案 B（采用） |
|---|---|---|
| 实现 | `ThreadPoolExecutor(48)` | `ProcessPoolExecutor(16)` |
| 实测 | **0.33 s/件**，40 分钟只跑完 20%，预计 4 小时 | **0.025 s/件**，全量 33,621 件 **11 分钟** |
| 优点 | 代码改动小 | 4–20× 提速 |
| 缺点 | trimesh 的 `mesh.process(validate=True)` 持 GIL，线程越多越慢（比串行 0.098 s/件 还差） | 每进程约 1.7 GB 内存 |

**结论**：采用进程池。这是整条流水线唯一一次"改动小、收益极大"的优化。

## 5. GPU 白名单：4 卡 → 8 卡

| | 方案 A | 方案 B（采用） |
|---|---|---|
| 白名单 | `(1,2,3,7)` | `(0,1,2,3,4,5,6,7)` |
| 实测 | 编排器传 `--gpus 0..7` 时 0/4/5/6 四个分片 argparse 报错秒退，**实际只有 4 卡在跑**，且日志看不出异常 | 8 卡全用 |
| 缺点 | — | 4/5/6 是另一位用户 `bosheng` 的常驻进程（GPU 利用率持续 0%、各 650–750 MiB）；用户确认"可以挤占"，若对方恢复计算则两侧各分一半 |

**坑**：白名单外的卡会让分片瞬间退出，编排器只看到"分片秒退"，很容易误判成 8 卡并行。

## 6. A4 分片数的反复

| 分片 | 卡/片 | 空载速率 | 优缺点 | 结论 |
|---|---|---|---|---|
| 8（1/卡） | 1 | 0.208 件/秒（单件 33.3 s） | 每卡有 71% 时间在等 CPU（加载/指标/导入） | 初期方案 |
| **16（2/卡）** | 2 | **0.292 件/秒** | 优点：+40%，两个分片互补填空；缺点：CPU 占用翻倍，与 A1/A2 抢 | 曾采用，后放弃 |
| 6 | 1（部分卡闲置） | 0.067（争用时） | A1/A2 拿到最多 CPU（0.187） | 否（A4 追不上） |
| 12 | 1.5 | 0.180（争用时） | A1/A2 掉到 0.107 | 否 |
| **10（冻结）** | 1.25 | 0.12–0.15（争用时） | 两侧速率接近 | **采用** |

**判断依据**：A4 只要有 0.12 件/秒就能跟上 A1/A2，多出的产能无处可用；所以"提 A4 产能"本身不缩短总时长，只有"降 A4 的 CPU 占用"才有意义。

## 8. 生产者调度：事件驱动 → 常驻线程 → 多组并发 → 回到单组

| 版本 | 机制 | 问题 |
|---|---|---|
| v1 | 每组 A4 结束时补一次 A1/A2 | 队列排空后 CPU 空转（实测只剩 3 个进程、负载 22） |
| v2 | **常驻补货线程**（10 s 一轮）+ `needs_a1a2()` 跳过已完成组 | 修好空转（保留） |
| v3 | `--producer-workers 3`（多组同时生产） | 3×8 分片 = 24 进程 → 负载 199 超订，吞吐反降 |
| **v4（冻结）** | 回到单组生产 + 22 进程 | 与 A4 分片数配合 |

另一个已修的缺陷：首个分片原先**同步等待**写完 `plan.json` 才并发其余分片，导致组内先串行跑一个分片（约 24 分钟）；改为后台 `Popen` + 轮询 plan.json。

## 9. 线程数实验（无效，已记录）

`vae3d/back_shell.py` 的 `cpu_scene()` 写死 `RaycastingScene(nthreads=8)`，`OMP_NUM_THREADS` / `MKL_NUM_THREADS` / `torch.set_num_threads` 都压不住。曾在 `run_initial_batch_single_thread.py` 里猴补丁成 `nthreads=1`：

- 单件：121 s（改前） vs 117–121 s（改后）→ **无差别**
- CPU：435–518%（改前改后一致）
- `--samples 4096 → 64`：121 s → 117 s，指标计算也不是大头

**结论**：open3d 射线本来就单线程执行，那 8 个线程基本空转；真正吃多核的是网格加载、A2 壳构造、指标计算。补丁保留（无害、结果一致），但不构成提速手段。每件约 **500 核·秒是算法成本，改参数动不了**。

## 10. 被否决的方案（连同否决理由）

| 方案 | 预期收益 | 否决理由 |
|---|---|---|
| **带内投票**（只在近表面 4 体素内投 98 向票） | A1/A2 省约 4× | 用户指出：A2 的门控面取自**整个** counts 场的 25% 等值面，候选点虽距网格 ≤3.73 体素，但决定它的门控面可能在更远处；截断投票场会造出错误/缺失门控面，改变带内 A2 值。且该池多开口/薄片/绕序不可靠 mesh，"带外符号显然"不成立。收益核算：4 体素带只覆盖约 23% 网格（8 体素 46%），只省约 4×；验证需 12–16 h 且无法与在跑的流水线并行，净收益仅 3–11 h，还牺牲与 g2 R256 基线的可比性 |
| **CUDA/OptiX 射线** | 单件 3–8 s | 服务器 Vulkan 实例建不起来（`Failed to create Vulkan instance`），CUDA 设备正常但 slang RT 只支持 Vulkan/D3D12；纯 CUDA 自写 BVH 无 RT 核，约 20–50 Mrays/s → 单件 33–83 s，工程量大收益小 |
| **3080 机器分担** | 单卡 ≈ 远程集群的 1/3 | 数据搬运：A1/A2 输出 135 MB/件，8 千件要回传 1.1 TB |
| **A4 预加载流水** | GPU 利用率 44.7% → ~80% | 实测 A4 只有 12.8 s 是 GPU 拟合、31.4 s 是 CPU 侧；且 A4 有 2.3 倍富余，提产能不缩短总时长。用户明确"8 卡冒烟先不做" |
| **R256 以下降到 R128** | 射线数降 8× | 分辨率是已验证的有效杠杆（R128→R256 Chamfer 2.9×），回退等于放弃实验主线 |

## 11. 工期估算的两轮修正（教训）

| 版本 | 算式 | 结果 | 问题 |
|---|---|---|---|
| v1 | `31,543 × 550 核·秒 ÷ 128 线程` | 35–38 h | 隐含"A1/A2 独占 128 核"且"A4 不吃 CPU" |
| v2（现） | `31,543 × (550 + ~200) 核·秒 ÷ 128` | 51 h 下限，实测 45–65 h | 补上 A4 的 CPU 成本；再叠加调度损耗 |

教训：**单阶段耗时不能当整机吞吐**，必须按「每件总核秒 × 件数 ÷ 总核数」算；历史记录里"A4 11.8 s/件"是单阶段、空闲机器上的数字，实际墙钟是 33–44 s。
